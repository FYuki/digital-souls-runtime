# AIキャラクター一貫性基盤 要件整理

- 状態：要件 Grill を反映（2026-11-14）、リポジトリ構成を追記（2026-11-20）。作業指示書・Epic ではない
- 表記：**[決定]** 本人決定 ／ **[推測]** AIの補足で本人未確認 ／ **[委任]** 実装・運用に任せる ／ **[未決]** 要判断
- 前提：既存の Core / Memory 分割構成と過去の ADR・決定は、引き継ぎ必須ではない [決定]
- 自作するか既存基盤を使うかは、この要件を評価軸にした調査で決める [決定]

## 1. 目的と背景

複数のチャネルから利用されるAIキャラクターが、どの経路から話しても同じ人物として振る舞う状態を担保する。

見直しの理由 [決定]
- Core と Memory を分けた構成で、2サービス間の契約と調整が重かった
- 要件が明確でなく、仕様が定まらず収束しなかった
- 開発中の知見がたまり、半年の間に AIRI・Hindsight など他のフレームワークも更新された

## 2. 対象範囲 [決定]

| 項目 | 内容 |
|---|---|
| キャラクター | 複数体。記憶と属性はキャラクターごとに完全に独立し、キャラクター同士は共有しない |
| 話し相手 | 主利用者1人と他者（配信の視聴者、会話に出てくる第三者） |
| 最初の対象チャネル | Web（文字チャット）、配信 |
| 後から対象にするもの | ゲームbot。音声は最初の対象に選ばれなかった（後から対象にするかは[推測]） |

## 3. 用語とキャラクターの属性

### 3.1 属性の分け方 [決定]

属性は意味で分け、各属性に「変化の種類」を持たせる。

| 意味の分類 | 属性 | 内容 | 変化の種類 | 最初の範囲 |
|---|---|---|---|---|
| 人格（Identity） | CoreIdentity | 名前・設定・世界観など、変化しない価値観 | 固定 | 対象 |
| | Temperament（気質） | 変化しない人格のコア | 固定 | 対象 |
| | SpeechStyle（口調） | 話し方 | 固定 | 対象（関係に応じて柔らかくなる動きは後続） |
| | PersonalityProfile（性格） | 経験などで変化する人格・価値観。カードに初期値を書く | 経験で変化 | 対象 |
| 関係 | 主利用者との関係 | 好意・信頼など（軸は[未決]） | 経験で変化 | 対象 |
| 気分 | 気分 | その時の状態 | 一時的 | 後続 |
| 近況 | 近況 | その時の自分の出来事・関心 | 一時的 | 後続 |

- 一時的な属性の想定ユースケースの1つ：内省で「次にやりたいことリスト」を更新する [決定]。どの分類に置くか（近況か、独立した属性か）は[推測]

- 関係の属性は主利用者に対してだけ持つ。他者との出来事は記憶として残す [決定]

### 3.2 変化の種類ごとの扱い [決定]

| 変化の種類 | 誰が変えるか | 反映 | 記録 |
|---|---|---|---|
| 固定 | 運用者がカードを編集する | 次の応答から | 版 |
| 経験で変化 | LLM が変化の向きと強さを提案し、システムが変化量を調整する | 会話の区切りで評価 | 理由、根拠の記憶ID、履歴 |
| 一時的 | LLM が上書きする | 即時。時間がたっても自動では戻らない | 最新値と直前の理由だけ |

- 経験で変化する属性について、システムは属性ごとに「1回あたりの変化の上限」と「値の上下限」を守らせる。上限の値は運用者が設定する [決定]。計算式は実装に任せる [委任]
- 性格の変化は自動で反映し、運用者が取り消せる [決定]

### 3.3 その他の用語

| 用語 | 意味 |
|---|---|
| チャネル | Web・配信など、キャラクターに話しかける入口 |
| 記憶 | 出来事（原文）と、そこから作った要約・事実 |
| 派生物 | 原文から作った要約・事実・埋め込み・変化理由 |
| 出典リンク | 派生物から元の原文をたどるための記録 |
| 忘却 | キャラクターの振る舞いとしての「忘れる」 |
| 消去 | 運用者が行う、システム上の個人情報の除去 |
| 墓標 | 行・ID・日時・つながりを残し、本文を `[filtered]` にした記録 |

## 4. 一貫性の定義

| 種類 | 定義 | 扱い |
|---|---|---|
| (a) | 自分についての事実・記憶と矛盾しない | 必達 [決定] |
| (b) | 固定の属性が保たれ、変化する属性は現在値どおりに振る舞う | 必達 [決定]。定義の文言は属性の分け方の選択肢の説明に含めて選ばれたもので、単独では確認していない |
| (d) | 変化する属性が変わるとき、理由が記録されている | 必達 [決定]。当初の「理由のない変化をしない」から変わった。文言は (b) と同じ経緯。記録の有無は評価セットではなくテストで測る性質になる |
| (c) | チャネルをまたいで会話が続いている | 必達としない [決定] |
| (e) | モデルを替えても同じ人物に見える | 必達としない [決定] |

- 消去は一貫性より優先する。消去によって生じた食い違いは (a) の評価対象にしない [決定]

## 5. 構成 [決定]

- 応答を作る入口は1つに限る。UI・APIは LLM を直接呼ばない
- 記憶の作成と属性の更新も、入口が担う。別サービス間の取り決めは持たない（入口の内部でライブラリを使うのはよい）
- 正本は論理的に1つ。物理的に1つのDBである必要はない
- 入口は複数インスタンスに増やせるようにしておく。実際に増やすかは応答の速さで判断する
- 場による違いは、長さ・形式だけ。それ以外の属性は場によって変えない
- 応答を生成する LLM はキャラクターごとに1つに固定する。変えるときは評価セットで確認する
- 会話履歴はチャネルごとに分ける。他の場の内容は記憶として思い出す [推測：質問の前置きで示しただけ。(c)を必達としない決定から導いた]
- リポジトリは digital-souls-runtime の1つ。中はモジュール単位（入口・記憶・属性・生成・消去など）で分け、依存の向きは検査で守る
- 別パッケージにするのは、独立した利用者がいるものだけ（例：チャネル用クライアント、評価ランナー）

## 6. 並行処理

- 想定：Web と配信など、常に応答が必要な処理を同時に動かす [決定]
- 同じキャラクターへの書き込みが同時に来ても、属性・記憶が壊れないこと [推測：並行処理の想定から導いた]。実現方法は実装に任せる [委任]
- 複数インスタンスにするかは、2チャネルから同時に送ったときの最初の応答までの時間を実測して判断する。想起にかかる時間も含める [未決・未実施]

## 7. 記憶

- 原文は会話のたびに保存し、要約・事実の作成は非同期で行ってよい [委任]
- 他の場で思い出せるようになるまでの遅れは、数分程度まで許す [決定]
- 記憶には公開範囲（私的／公開）を持たせる。私的な記憶は配信では文脈に入れない [決定]
- 視聴者は配信サービスのIDだけで識別し、他のチャネルとは結びつけない [決定]
- UIから記憶を削除する機能は持たない [決定]

## 8. 忘却 [決定]

- 「忘れて」と頼めるのは、主利用者と、自分の発言に限って他者
- 頼まれた記憶は、自発的な想起の対象にしない。相手が同じ話を再び持ち出したときだけ参照してよく、「前にも聞いた気がする」程度の反応を許す
- 「忘れてと言われたこと」自体は覚えている
- 忘れた記憶がきっかけで変わった関係・性格は、そのまま残す
- 忘却はすべてのチャネルで効く [推測：記憶をチャネル間で共有する決定から導いた]

## 9. 個人情報

### 9.1 情報の分類と保存範囲 [決定]

場の公開度はチャネルごとに固定する（例：Web は私的、配信は公開）。

| 分類 | 例 | 私的な場 | 公開の場 |
|---|---|---|---|
| 秘密情報 | APIキー、パスワード、管理者の住所 | 保存しない | 保存しない |
| 要配慮情報 | 病歴など | 保存する | 保存しない |
| 通常の情報 | それ以外 | 保存する | 保存する |

- 主利用者が私的な場で話した第三者の要配慮情報は、私的な記憶として保存する
- 派生物（要約・事実・変化理由の本文）は、元になった記憶のうち最も厳しい公開範囲を引き継ぐ
- 関係・性格の変化した値そのものは、公開の場でも振る舞いに使う
- 私的な記憶は配信の文脈に入れない（7章）

### 9.2 検出 [決定]

| 対象 | 時点 | 初期の方法 | 後続 |
|---|---|---|---|
| 秘密情報 | 受け取った時点。伏せ字にして、LLM にも会話履歴にも渡さない | システムで担保できる範囲：決まった形のもの（キー・トークンなど）のパターン照合と、運用者が登録した文字列との一致 | ローカルの BERT による判定を足す |
| 要配慮情報（公開の場） | 保存前（記憶を作る非同期処理） | LLM による判定。取りこぼしは保守用の消去で補う | BERT への置き換えか併用 |
| 全般 | 出力時 | ブラックリストで確かめる | — |

- 秘密情報の検出は、誤検出が増えても見逃しを減らすことを優先する [推測：見逃しの影響が大きいことから導いた]

### 9.3 消去 [決定]

| 項目 | 内容 |
|---|---|
| 対象者 | 主利用者、会話に出てくる第三者、配信の視聴者 |
| 実行者 | 運用者のみ。依頼を受けた場合も、窓口は運用者 |
| 範囲 | 原文（会話履歴・キャラクター自身の応答を含む）と派生物 |
| ログ・バックアップ | 定期削除で消えるまでは残ってよい。保持期間は運用で決める |
| 外部 LLM 側の記録 | 対象外 |
| キャラクターから見え方 | 墓標は文脈に出さない |
| 発言者の情報 | IDと名前は消し、「視聴者」「主利用者」などの種別だけを残す |
| 属性への影響 | 変化した値は残し、変化理由の本文だけを墓標にする |
| 監査記録 | 誰が・いつ・どの記録を消したかだけを残し、何を消したかは残さない |
| 保守機能 | 機微情報が混入したときの消去機能を、通常機能とは別に用意する |

### 9.4 消去の手順 [決定]

1. 運用者が、消す対象（記録、または人の種別とID）と、消す語を指定する
2. 出典リンクをたどって影響範囲を特定し、原文・会話履歴・応答を墓標にする
3. 影響を受けた派生物と埋め込みを、残った原文から作り直す
4. 正本（原文・会話履歴・応答・派生物・属性の変化理由・応答記録）を消す語と元の文で検索し、残りが0件であることを確かめる。埋め込みは語で検索できないので、出典リンク上の対象がすべて作り直されたことで確かめる。結果を運用者に報告し、どちらかが満たされなければ消去を完了扱いにしない。ログ・バックアップは検査の対象外（定期削除で消える）
5. 消す語を出力時のブラックリストに登録する。ブラックリストだけは、消した語を保持する例外になる（持ち方は[未決]）

- 出典リンクは、すべての派生物に必須とする（変化理由の「根拠の記憶ID」も同じ仕組みを使う）
- 普段は使わない機能なので、処理が重いことは許容する。「確実に消せたこと」の担保を優先する

## 10. 記録とたどれること [決定]

- 応答ごとに、使ったカードの版・変化する属性の値・モデル・思い出した記憶のIDを記録する
- この記録は、消去時に応答の範囲を特定する出典リンクとしても使う

## 11. 検証 [決定]

- 一貫性の受け入れは、(a)(b)(d) を測る固定の評価セット1つに集約する
- 忘却・公開範囲・消去などの機能は、通常のテスト（UT/IT）で確かめる
- 合否は LLM が自動で採点し、判定が割れたものと一部を抜き出したものを本人が確認する
- プロンプト・モデル・文脈組み立てのコードを変更するときは、評価セットを通らなければ反映しない
- カードの編集はすぐに反映し、あとから評価セットを回して結果を知らせる
- 開発の進め方は TDD と TAKT（記録上の本人の既定。今回の会話では確認していない）

## 12. スコープ外 [決定]

- UIからの記憶削除
- 外部 LLM 側の記録の消去
- キャラクター同士での記憶の共有
- 他者（視聴者など）との関係の属性
- 最初の範囲では：気分、近況、関係に応じた口調の変化、ゲームbot、音声

## 13. 未決事項

1. 応答の速さの目標値（Web・配信それぞれ）。複数インスタンスにするかの判断基準になる
2. 主利用者との関係の軸（過去の記録では好意・信頼・近さの3軸）
3. 評価セットの合格基準値（最初に基準となる値を測ってから決めることを想定）
4. 第三者の個人情報（要配慮情報以外）をどう見分けるか。消去時に対象者を特定するために必要
5. 常連の視聴者（サブスクなど）を同じ人として結びつけるか（別途検討）
6. 配信で私的な件を聞かれたときの振る舞い（(a)と公開範囲の優先関係。例：知らないふりをするか、「それはここでは話せない」と言うか）
7. 秘密情報・要配慮情報の具体的な一覧（何を秘密情報とし、何を要配慮情報とするか）
8. 評価セットの単位：キャラクターごとに持つか、共通の型にするか
9. 配信での「会話の区切り」の定義（関係の評価と記憶作成のタイミング）
10. ブラックリストに残る消去語の持ち方（ハッシュ化など）。監査記録の「何を消したかは残さない」との兼ね合い
11. フレームワークの再調査
   - 対象候補：AIRI と Hindsight の更新内容、似た分野の新しい候補
   - 必須の評価軸：本書の要件、特に 5章（入口が書き込みも担う）、3.2（変化の種類ごとの書き込み）、9.3（出典リンクと作り直しによる消去）

## 付録：ADR 候補

次の3つは、後から変えるのが難しく、背景を知らないと理由が分かりにくく、実際に別の案と比べて選んだものなので、ADR に残す候補とする。

1. **入口が読み書きを一手に担う**：Core と Memory の分割をやめる。比べた案は、記憶を別サービスにする構成
2. **UIからの削除なしと、運用者による消去**：墓標・出典リンク・作り直し・残存検査で消去する。比べた案は、行ごと削除、中立な要約への置き換え、内容検索で派生物を探す方式
3. **属性を意味で分け、変化の種類ごとに書き込み方を決める**：比べた案は、不変／変化で分ける方式
